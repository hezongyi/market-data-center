# v0.6.0 — production task registry and unified scheduler

This feature release adds the production task and unified scheduler described by
`docs/specs/2026-09-14-maintenance-scheduler.md` (AC01–AC24) and implemented in
five stages per `docs/plans/2026-09-14-production-task-scheduler.md` (S0–S5).
It changes the ledger schema, adds an HTTP surface and a Web UI workspace, and
introduces a scheduler service. **The scheduler starts in shadow mode**: it
records what it *would* dispatch until an operator enables dispatch, so this
release can be activated without changing how data is produced.

## Changes

- **Ledger foundation (S0–S1)**: ordered migrations to `SCHEMA_VERSION=5`
  (production semantics, fixed inputs, manual retry linkage, governed provider
  backoff), idempotency reserved/applied/answered in one transaction and bound to
  request content, ownership as append-only history, and one dependency-free
  ISO-8601 parser so Python 3.10 accepts the same instants as 3.11/3.12.
- **Scheduler (S2–S4)**: a bounded, auditable tick (indexed due scan, coalesced
  triggers, lease with fencing, global dispatch switch, shadow mode), real
  dispatch that writes steps/runs/jobs/ownership in one transaction, closure from
  run outcomes, coverage-driven raw planning (observed tail → gaps past their
  cooldown → recorded backlog), derivation planned per contiguous run of whole
  target buckets so a missing bar blocks only the bucket that covers it, fixed
  inputs rebuilt from persisted references, a capacity gate that refuses new
  publishing work when the disk is critical, and a provider backoff persisted from
  spent retry budgets.
- **Console and read models (S5)**: `/production/tasks` (cursor paging, filters,
  create, preview, PATCH with `expected_version`, actions, history, steps,
  retry), per-plan `phase`/`health`/`block_reason`, the catalog matrix, the
  governance unit list, a scheduler view with the capacity gate and provider
  backoff, and the Production plans workspace (registry, wizard, edit under an
  optimistic lock, lifecycle controls, recorded-boundary panel).
- **Deployment and operations**: activation verifies every restarted unit's own
  state (scheduler included) and records it; `retention-audit` runs as its own
  unit with its own receipt action instead of an `ExecStartPost` of provider
  acceptance; the runbook documents the scheduler service, the two switches that
  gate dispatch, the service drill and the legacy timer takeover.
- **Takeover preparation (not executed)**: `data_center.takeover` inventories the
  declared units and the host's own units (including `ExecStart` and cadence),
  imports legacy entries as **paused** plans, reports an unknown scope instead of
  widening it, and verifies that no legacy unit is still installed and no two
  plans hold one ownership key.

## Compatibility and migration

- **Ledger schema 1→5**: applied automatically and repeatably by any component
  that opens the database (API, worker, scheduler). Existing runs, tasks,
  progress and receipts are preserved; the upgrade path is covered by
  `backend/tests/test_scheduler_service_drill.py`.
- **Contracts**: new fields (`phase`, `health`, `block_reason`, `capacity`,
  `provider_backoff`, `services_active`) and new stable error codes
  (`filter_error`, `version_conflict`, `expected_version_required`,
  `capacity_protected`). Existing fields and routes keep their meaning.
- **No new configuration is required.** Dispatch stays off unless
  `DATACENTER_SCHEDULER_DISPATCH_ENABLED` is set *and* the global switch is
  resumed; the unit itself passes no `--dispatch`.
- **Rollback**: the previous release (`3e2362ab0b31-6005b252`) remains the
  rollback target. A rollback restores the previous binaries; the schema stays at
  version 5, which older code refuses to open rather than mis-reading it, so a
  rollback must be decided before activating the scheduler delivery or performed
  with a prepared database restore.

## Production activation (separate approval)

The scheduler unit is **not** installed and the scheduler is **not** running in
production. Activation order agreed for this release: activate the release
(retention audit verified first), observe the scheduler in shadow mode for at
least four hours against the legacy timers, then import the legacy entries as
paused plans, stop the legacy units and enable a single `dukascopy/EURUSD`
canary before widening. Each step keeps its own receipt; widening needs a fresh
go/no-go.
