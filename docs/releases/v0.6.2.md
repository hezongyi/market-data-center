# v0.6.2 — governed provider gaps and release evidence

This patch release corrects two failures exposed by the first v0.6.1 production
canary. It retains ledger schema 5 and stores pageable, restart-safe provider-gap
debt in a backward-compatible indexed TaskProgress backing table. The canonical identity and stored
receipt format do not change; the capabilities contract adds `provider_gap` to the
documented `production.block_reasons` enum.

## Changes

- A provider response whose only finding is `coverage_not_ready` no longer
  spends the worker's three short retries and becomes a misleading dead letter.
  The terminal run remains immutable as `failed`; its raw step is classified as
  `provider_gap`, the execution closes `completed/degraded`, and the exact
  missing range is retained as governed gap debt.
- Provider-gap cooldown applies to a gap first observed in an ordinary
  ingest/tail run as well as a later `gap_repair` run. Other tail windows,
  symbols and providers remain eligible while that exact range cools down.
  Structural or mixed quality findings remain failures.
- The Release workflow waits for a successful `verify` check on the tag's exact
  protected-main commit. Missing or unparsable CI evidence now fails before
  receipt generation instead of passing an empty run ID downstream.

## Production incident evidence

On deployment `aca73a045275-c6470772` (`v0.6.1`), EURUSD canary execution
`9b30a301-deaa-4d14-9e8e-6cc78dab24d7` and its automatic fixed-delay successor
`be124b50-8128-4d9f-aaa5-322cf253fb52` each reached a dead letter after three
identical coverage attempts. Their responses contained only
`coverage_not_ready`; the first requested 14 one-minute bars and received 13,
with the missing timestamp at `2026-09-14T22:19Z`. Global dispatch was paused
through the audited operations API at `2026-09-15T01:51:39Z`, after queued and
running work had reached zero.

The v0.6.1 tag itself is intact. Its first Release run failed because the tag
was pushed before the merge commit's `verify` completed; the workflow accepted
an empty lookup result and receipt generation could not parse the empty run ID.
The v0.6.1 Release/receipt must be completed separately without moving that tag.

## Verification and acceptance

- The isolated regression follows task → execution → step → run and asserts a
  single failed provider-gap run, a degraded execution, exact persistent gap
  debt, cooldown, and unchanged structural-failure behavior.
- The release workflow contract asserts bounded waiting for commit-scoped
  `verify` and rejection of empty CI evidence.
- Repository unified CI, hosted commit-scoped checks, immutable release and
  production acceptance are recorded in the release checklist and in the TA
  evidence index before this release is declared accepted.

## Rollback

Pause global dispatch, let in-flight work settle, and activate the previous
verified deployment. Restore a legacy producer only after verifying its runner
identity and selector scope; the old derived unit previously referenced a stale
checkout, so merely enabling its timer is not a valid rollback. Schema 5 remains
unchanged, and historical runs, plans and gap debt are not
rewritten.
