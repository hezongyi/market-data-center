# v0.4.0 — WebUI data workbench

Feature release. The API envelope (`v1`), dataset schemas, manifest, run
receipt and backup formats stay compatible with v0.3.3. What changes is the
write surface: maintenance work is queued through one contract, and two
endpoints change behaviour (see **Contract changes**).

## Highlights

- **Unified maintenance task center.** `POST /api/v1/maintenance/plans`
  validates a request and previews its windows, coverage, input snapshot and
  capacity impact without queueing anything; `POST /api/v1/maintenance/tasks`
  queues it and returns one envelope (`task_id`, `run_ids`, `window_count`,
  `plan_id`, `input_snapshot_id`, `capacity`, `audit_id`). `ingest`, `backfill`,
  `gap_repair`, `derive`, `quality` and `parity` all use it. `/derive/runs`,
  `/economic/ingest` and `/quality/checks` return the same envelope.
- **Read-only verification runs.** `quality` and `parity` runs record findings
  and publish no canonical part and no manifest.
- **Run read models.** `GET /api/v1/runs` supports status/dataset/run
  kind/scope/time filters with opaque cursor paging; `GET /api/v1/runs/{id}/detail`
  projects stage, windows, input snapshot, manifest status, degraded reasons and
  the retry chain without rewriting the stored receipt.
- **Finding governance.** Findings carry a stable `finding_id`, observation
  counts and an `open|acknowledged|resolved` handling state that stays separate
  from run results; `GET /quality/findings` filters server-side.
- **Data-asset workspace.** `GET /api/v1/capabilities` publishes datasets,
  providers, instruments, recipes and the run-kind × dataset matrix;
  `GET /api/v1/market-bars/coverage` adds recipe semantics to derived coverage.
  The Explorer queries derived market bars with the same cursor, snapshot and
  schema semantics as raw bars.
- **Operations.** `GET /operations/queue`, `/operations/worker`,
  `/operations/capacity-history`, `/operations/receipts` and `/operations/audit`;
  capacity history shows only monitor-recorded transitions and the audit stores
  a non-reversible actor fingerprint, never a credential.
- **Web UI.** Maintenance, Runs, Catalog, Explorer, Quality and Operations
  workspaces in React 19/Vite, served by the API, at 1440px and 390px.

## Contract changes

- `POST /api/v1/quality/checks` is now asynchronous: it returns **202** with a
  queued run envelope instead of a synchronous `200` result. Findings are read
  from `GET /api/v1/quality/findings` after the run completes.
- `POST /api/v1/economic/ingest` returns the unified queued envelope (still
  `run_id` + `status`, plus `run_ids`/`window_count`/`capacity`).
- Write failures now carry stable semantic codes (`unauthorized`,
  `capacity_protected`, `invalid_request`, `not_found`, `conflict`).
- Run kinds are constrained per dataset; a combination outside the matrix is
  rejected with `unsupported_run_kind` at planning time.
- Every mutating endpoint except the side-effect-free `POST /maintenance/plans`
  requires `X-API-Key` when `DATACENTER_API_KEY` is configured, and every
  mutating endpoint now appends to the write audit trail.

## Verification

The release branch must pass the protected-main `verify` check: backend tests on
Python 3.10/3.11/3.12, Ruff, dependency and compatibility checks, secret scan,
operations acceptance, snapshot benchmark, Web build, isolated browser
acceptance at 1440px and 390px, and service restart acceptance. Browser
acceptance covers provider ingest, derive, parity, degraded quality
verification, economic ingest against a local provider fixture, a refused
write, a capacity-protected write, the run-kind matrix, finding handling state
and the operations panels.

Production activation must retain stage and activation receipts and verify
readiness, metrics, smoke, and the API/worker deployment identity against the
immutable tag.
