# v0.3.2 — provider 覆盖不完整同样按 degraded 处理

Patch release；`/api/v1` 与既有 dataset 查询契约保持兼容。

## 修复

`v0.3.1` 部署后，生产 1m maintenance 仍在报 `result=failed`。回执显示 provider gap 的分级已经生效（14 个窗口为 `degraded`），但另有 2 个窗口以 `QualityError: coverage_not_ready` 失败。

`coverage_not_ready` 表示 provider **返回了数据但窗口内缺内部分钟**——与 `ProviderGapError`（完全没有数据）是同一 provider gap 现象的另一条路径。代码库本身已经这样理解它：该 finding code 只在 `ingest/service.py` 的窗口覆盖检查中产生，`ingest/process.py` 明确把它视为可重试的 provider 覆盖信号（"structural/schema quality failures remain final"），`maintenance_runner` 早已在 gap-isolation 与 cooldown 逻辑里特判它。

现在窗口被判为 `degraded` 的条件为：

| 情况 | 判定 |
| --- | --- |
| `ProviderGapError`（provider 完全没有数据） | `degraded` |
| `QualityError` 且 findings 全部为 `coverage_not_ready` | `degraded` |
| `QualityError` 含结构性 finding（`ohlc_inconsistent`、`negative_volume`、`lineage_incomplete` 等） | `failed` |
| 覆盖率 finding 与结构性 finding 混合 | `failed` |

gap-isolation 与恢复窗口调度对 degraded 窗口照旧执行；数据永不合成。

### 同时包含的其他修复

- **浏览器验收的容量检查确定性**：`scripts/browser_acceptance.cjs` 原以 `warning_free_ratio=0.99` 制造 warning 状态，而该阈值只有在 `tempfile.gettempdir()` 所在文件系统被占用 >1% 时才成立，空 tmpfs 上容量 UI 检查必然失败。改为通过新的 `Settings.capacity_fixed_free_ratio`（`DATACENTER_CAPACITY_FIXED_FREE_RATIO`）固定测量值；配置了 deployment manifest 时使用该值会报错，因此真实部署无法伪造自身容量测量。
- **时序脆弱测试**：delivery 预算断言改为语义界限（至多两次尝试后由预算终止重试循环），不再依赖墙钟时间。
