# v0.6.1 — expected empty windows, grid-aligned coverage scans, takeover evidence

This patch release fixes three defects the production takeover surfaced. It does
**not** change the ledger schema (`SCHEMA_VERSION=5` stays), the HTTP contract or
any stored format, and it can be activated without changing how data is produced:
dispatch remains an operator action.

## Changes

- **An empty input window is classified instead of crashing (PR #117).**
  `TransformExecutor.derive` resolved the session profile from the first input
  row, so a window without rows raised `IndexError` before the empty-input check
  could classify it; every such run was retried three times and dead-lettered,
  which is how the legacy derived maintenance unit ended up rate-limited and
  stopped (25 `dead_letter` derive runs carry that signature). The session is now
  resolved from the selector, and the two expected conditions have names:
  `SessionClosedError` when the session profile keeps the whole window closed
  (reported once, never retried) and `ProviderGapError` when an open window has no
  usable input — missing rows, a partial bucket under `missing_input_policy="fail"`,
  no complete output bucket, or coverage that is not ready. Per spec 5.4 a
  confirmed source gap stays degraded and never manufactures a failed run; the
  derived planner skips a session-closed window instead of spending a run and its
  retries to rediscover it and reports `skipped_count`; the run view explains a
  closed window as `session_closed` without blaming the provider.
- **A coverage scan starts on the bar grid (PR #118).** A plan's
  `window_policy.history_start` comes from an import clock and carries seconds,
  while `evaluate_coverage` steps from that boundary without aligning it: a scan
  starting at `23:03:30` expects bars at `:30` seconds, so every published bar
  looked missing. Measured against the production catalog for
  `legacy-dukascopy-EURUSD-1m`, same instant, only the start differs:
  `missing=1380/1380 not_ready` as stored versus `missing=0 ready` when floored.
  All nine imported plans carried that value, so the first enabled round would
  have refetched about 49 hours of already-canonical history. `coverage_scan_window`
  now floors its start onto the raw timeframe grid (an existing plan needs no
  ledger edit) and `takeover._history_start` floors what it writes.
- **The takeover tool reports the scope it knows (PR #116).** The
  provider-agnostic allowlist is no longer narrowed invisibly: each comparison row
  carries `symbols`, `importable_symbols`, `unapproved_symbols` and
  `unserved_symbols`, and `partially_served` names every unit that cannot import
  everything its own allowlist named. A unit that runs a wrapper is followed
  (`exec`/`source`, depth ≤ 3, only the wrapper's own literal variables) to the
  runner's real command, so a live capture of the macro-market-lab entry now reads
  its provider, symbols and recipes instead of leaving the derived half to a
  hand-written inventory. The runner is a field rather than a comment appended to
  the command line, a derived entry whose recipes resolve to no output is
  `unmappable`, `verify` compares the full schedule shape (including a daily
  plan's timezone and local time), `--price-basis` reaches `plan` and `verify`
  too, and `installed_not_declared` compares against the repository's own unit
  files and the governance timers.
- **Browser acceptance targets the dataset row, not any matching text.** The
  catalog check passed only while the lineage and capability panels had not
  rendered; it is now scoped to the "Data catalog" panel.

## Compatibility and migration

- Ledger schema is unchanged at 5; no migration runs and both directions of
  rollback keep working.
- Manifest, run receipt and operational receipt formats are unchanged. Two
  additions are visible in evidence: the derived maintenance receipt reports
  `skipped_count`, and a comparison row reports the scope columns above.
- The HTTP surface is unchanged; run views gain a `session_closed` degradation
  reason.
- Existing plans need no edit: the coverage alignment happens at read time. An
  operator who prefers the stored boundary to match can update the plan
  definition, which is an ordinary versioned change.

## Production activation (separate approval)

The release is staged from a clean checkout of this commit and activated through
`data_center.deployment activate`, which verifies every restarted unit's own state
and records the canonical and ledger hashes. Dispatch stays in shadow mode until
an operator enables it, so activation alone changes no data production. The
cutover itself (narrow canary, then the remaining plans, then blocking the legacy
units) is executed per `docs/operations-runbook.md` and recorded in the takeover
receipts.

## Rollback

- Pause dispatch (one operations action) and re-enable the legacy units; the
  schema is unchanged, so the previous release opens the same ledger.
- `data_center.deployment rollback <previous deployment id>` restores the previous
  release and verifies readiness, smoke and the unchanged data hashes.
