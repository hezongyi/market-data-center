# v0.4.1 — operations receipts panel

Patch release following the v0.4.0 production walkthrough. The API and dataset
contracts are unchanged from v0.4.0; this release fixes what the console shows
for operational receipts and adds the acceptance guard that locks it in.

## Fixes

- `GET /api/v1/operations/receipts` looked for `release` and `deployment`
  receipts, names the platform never writes. The Operations console therefore
  reported "No receipt recorded" for the stage, activation and rollback records
  that do exist. The action list now matches the actions actually recorded under
  the evidence root (`backup`, `backup_verify`, `restore`, `recovery_drill`,
  `capacity_check`, `deployment_stage`, `deployment_activate`,
  `deployment_rollback`, `deployment_runtime_failure`, `monitor`,
  `derived_market_bars_maintenance`, `real_release_webui_acceptance`,
  `post_release_rehearsal`).
- The console no longer keeps its own copy of that list: it renders the actions
  the API reports, so a name the platform never writes cannot appear as a
  phantom gap and a recorded receipt cannot be hidden by a stale copy.

## Verification

- Backend contract tests cover receipts surfacing under the action they were
  recorded with, and that names the platform does not write are absent.
- Browser acceptance asserts the receipts panel renders `deployment_stage` and
  never renders `release`/`deployment`; the assertion fails on the pre-fix
  console.
- The release branch must pass the protected-main `verify` check: Python
  3.10/3.11/3.12 backend jobs, Node 22 browser acceptance at 1440px and 390px,
  and aggregate `verify`.

## Rollback

Roll back to the previous verified immutable deployment (`v0.4.0`,
`5dfc1b1c6803-377c1193`) with the deployment module; do not modify canonical
parts, manifests, terminal receipts, or the ledger.
