# v0.3.0 — Dukascopy 1m 平台、派生 bars 与 consumer 切换

Additive release；`/api/v1` 与既有 dataset 查询契约保持兼容。

- Provider：新增 Dukascopy 历史 BID 1m ingest；`backend/pyproject.toml` 增加 `pandas>=2` 与 `dukascopy-python==4.0.1`。raw 仅 BID，ASK/MID 不在本版本范围。
- Legacy 边界：Dukascopy legacy 数据域只做只读盘点，published parts 默认从 legacy inventory 排除，不参与新写入。
- Derived：5m/15m/30m/1h/4h/1d recipe 与 snapshot-aware derived maintenance runner。高周期完整历史受 coverage 约束，provider gap 不补造；derivation 失败按 `degraded` 分类而不是伪造数据。
- Maintenance：受治理的 1m 计划维护，按 provider lag 上界与短窗口分片；session calendar 覆盖 Dukascopy FX 日切；遇到 provider gap 时隔离该 gap 并继续推进 tail，恢复窗口去重，瞬时 coverage gap 有界重试。
- Query：bar 查询窗口统一为 half-open 语义，parity 窗口语义与 consumer 运行时一致；readiness 按已观测 coverage 窗口判定，并暴露 ready intervals。
- Web UI：operations console 现代化（总览、runs 视图），生产 operation 与 degraded readiness 对齐。
- Deployment/observability：immutable deployment manifest 与 activation 身份一致性，ledger 完整性证据，backup 期间对 sqlite ledger 做快照以消除 recovery drill 竞态。
- Governance：`docs/current-state.md`、文档入口与 spec 状态规则；文档一致性检查纳入 CI。

## 运行时与依赖

- Python 3.10/3.11/3.12；Node 22。
- 三个 Python minor 各自使用 committed constraints（`backend/constraints/py310.txt`、`py311.txt`、`py312.txt`）。
- 生产依赖基线：FastAPI 0.115+、Pydantic 2+、Polars 1+、DuckDB 1+、`pandas>=2`、`yfinance==1.7.0`、`curl_cffi==0.16.3`、`dukascopy-python==4.0.1`。

## Compatibility

`/api/v1` envelope、`provider_bars.v1`、`economic_observations.v1/v2`、已发布 manifests 与 terminal run receipts 保持可读。Backup v2 仍是写入默认，v1 restore 继续支持。`operational-receipt.v1` 仅做 additive 扩展。

## Protected-main evidence

本 release 的 protected-main commit 必须带有成功的 commit-scoped `verify` check，且该 commit 是 `origin/main` 的祖先。`Release` workflow 在标签推送后生成并发布 `release-receipt.json`，其中记录 tag、commit 与 CI run id。实际 run 记录补充在 `docs/release-checklist.md`；历史 receipt 与标签不可变。

## Rollback

检出一枚此前已验证的不可变标签（`v0.2.0` → `54f002580a5c72cdd3da57ef12ffa14ea0f6c8c4`），安装该标签匹配的 `backend/constraints/py<minor>.txt`，保留 canonical history，重启 API/worker，然后运行 readiness、smoke 与 query parity。回滚不移动任何 release 标签。
