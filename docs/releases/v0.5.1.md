# v0.5.1 — operator-readable state reporting

This patch release collects the correctness and readability fixes merged into
protected `main` after `v0.5.0`. It changes API response metadata, Web UI
presentation, the real-provider acceptance receipt, and one CI gate; it does not
change stored contracts, add migrations, or require new configuration.

## Changes

- **Web UI hand-off between workspaces** (#82, #83): a maintenance request
  prefills only the fields that were actually established elsewhere, names the
  source of each prefilled field, reports a dataset/run-kind mismatch instead of
  applying a window that does not belong to it, and the quality and catalog
  views hand off the facts they already know.
- **Explorer submit semantics** (#84): the bars-mode submit is labelled
  `Load bars and coverage`, and values the response did not compute read as
  `Readiness not computed`, `Scope not computed`, and
  `Not computed by this response` instead of being presented as results.
- **Detailed coverage is explained when absent** (#85): `/provider-bars/coverage`
  returns `coverage_detail_unavailable` with the reason (missing window, no
  rows, unsupported part shape) instead of an empty detail object.
- **Capacity measurement provenance** (#86): capacity snapshots, capacity
  history events, and `/health/ready` report `measurement_source` (`live` or
  `fixed_acceptance`), and the Web UI presents a pinned acceptance measurement
  as pinned rather than as live state.
- **Real-provider acceptance is diagnosable from its receipt** (#94): every
  attempt records `category` (`timeout`/`network`/`http`/`contract`/`internal`),
  `retryable`, `error_type`, `error_message`, an `http_status` and a redacted
  response summary where applicable, and the adapter version. Only retryable
  categories are retried, with three bounded attempts.
- **Warning gate** (#95): FastAPI's app-creation alias warning is the single
  pydantic `UnsupportedFieldAttributeWarning` excluded from the gate; every
  other warning still fails it.
- **Production configuration guard** (#92, #93):
  `scripts/production_env_check.py` fails the backend gate when a deploy unit's
  `EnvironmentFile` can resolve to a repository checkout, and `--installed`
  audits the machine-level units and drop-ins.

## Verification

The protected-main post-merge checks must pass Python 3.10/3.11/3.12, Node 22
browser acceptance, and aggregate `verify`. The unified local gate
(`bash scripts/ci.sh all`) and its operational receipt must pass on the tagged
commit. Release staging and production activation must follow the immutable
deployment checklist with isolated smoke, backup/recovery, readiness, rollback,
and retained receipts.

## Provider acceptance observation

Checklist step 8 keeps the scheduled real-provider acceptance outside the CI
gate and treats it as a release observation. At the time of this tag the most
recent retained run (2026-09-14T01:00:21Z) records `binance` failing with
`ValueError` and `dukascopy` failing with `HTTPError`, while `yfinance` and
`fred` pass; the internal run receipts for the same window are `pass`, and the
receipts cannot say whether `HTTPError` was a platform refusal or an upstream
5xx. Those receipts predate the classification added by this release, so a
classified result requires a run under `v0.5.1` or later. This release therefore
claims no provider-level green, and the triage rules recorded in issue #94
apply to the next run.

## Deployment

This tag prepares the release; production activation is deliberately deferred
to a separate approval and a maintenance window. Until it is activated,
production continues to serve `v0.5.0` (`3e2362ab0b31-6005b252`), and this tag
touches no canonical part, manifest, terminal receipt, or ledger entry.

## Rollback

Roll back to the prior verified immutable deployment (`v0.5.0`) using the
deployment module if a future activation of this release fails; do not modify
canonical parts, manifests, terminal receipts, or the ledger.
