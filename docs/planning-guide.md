# Spec 与切片实施计划编写指南

维护者于 2026-09-16 确认采用“规划 agent 明确需求与切片，实施 agent 完成交付闭环”的协作方式。本文约束规划产物，不新增产品要求，也不改变既有开发、评审、合并和生产授权规则。

开发与验收流程以[开发指南](development-guide.md)为准；当前产品基线和路线图从[文档入口](README.md)读取。规划与实施可以由不同会话的 agent 承担，不意味着自动启动子代理。

## 1. 文档分工与输出规模

**切片不是 plan：切片是可独立实现和验收的小交付，plan 是组织这些切片的实施计划。**

| 产物 | 回答的问题 | 不承担的内容 |
| --- | --- | --- |
| spec | 要做什么、不做什么、哪些保证不能破坏、怎样算通过 | 逐文件施工步骤、日常进度 |
| plan | 切成哪些交付、依赖和顺序是什么、每片如何验收、当前进展如何 | 另写一套需求或降低 spec 验收标准 |
| 切片章节 | 本片交付什么、边界与依赖是什么、实施者如何完成闭环 | 重复抄写整份 spec |

默认一份 spec 加一份 plan，切片集中放在 plan 中，每片一个章节：

```text
docs/specs/YYYY-MM-DD-<topic>.md
docs/plans/YYYY-MM-DD-<topic>-implementation.md
```

- 已有适用 spec 或 plan 时优先更新，不因换 agent 或进入下一切片而另建同义文档。
- 新能力或数据、接口、权限等关键契约变化需要 spec；已有契约内的小功能、修复可以只用 plan 中的一张任务卡，极小任务可直接使用交接消息。
- 只有切片内容过长或确需独立交接时才拆文件；主 plan 保留索引和依赖，不重复维护正文与进度。
- 本 repo 当前产品迭代沿用既有实施路线图。新增专项 plan 时，由路线图链接到它，详细切片进度只在所属 plan 维护，不建立第二套相同状态表。
- 总 spec 覆盖已确认的整体范围；近期准备实施的切片写细，后续先列目标、依赖及验收编号，执行前再细化，不提前写大量施工细节。

## 2. 规划步骤

1. 读取适用 AGENTS、当前 spec、plan 和相关代码，核对已有实现、未完成项及历史证据，避免重复安排已完成工作。
2. 明确用户目标、范围、非目标和关键约束；区分已确认决策、合理假设与待决问题。已有授权不重复询问，影响需求或权限边界的未决问题不能假装已确认。
3. 先写可观察的验收标准，再按可交付结果切片，映射每个验收编号的责任切片；跨切片的整体旅程明确收口位置。
4. 为近期切片补足依赖、操作步骤、预期与证据要求；文件落点可以作为建议，除非属于必要契约，不强制函数签名和具体实现路线。
5. 自查需求覆盖、依赖、规则冲突和链接，交付 spec/plan 路径与可开始的切片。规划请求本身不授权实施、启动其它 agent 或外部操作。

阻塞本片的未决问题应写清影响；不受影响的已授权工作可以继续。获得规划批准后，只在范围或关键契约发生实质变化时重新确认，不逐切片机械索取批准。

## 3. Spec 模板

以下为结构模板，填写实际内容并删除无关章节；状态遵循[文档状态规则](README.md#状态规则)，未经批准不填 approved。

```markdown
# <能力名称>规范

日期：YYYY-MM-DD
状态：draft
依据：用户需求、适用规范与已确认决策的链接
关联计划：对应 plan 链接

## 目标与用户流程

谁在什么场景下，通过哪些动作获得什么结果。

## 范围与非目标

本轮包含、明确排除、保留的兼容行为。

## 关键约束

适用的数据身份、正确性、权限、并发、恢复、接口及 UI 保证。
引用已有契约，只写本次新增或改变的要求。

## 验收标准

| 编号 | 前置条件与操作 | 可观察的预期结果 | 证据要求 |
| --- | --- | --- | --- |
| AC01 | 具体环境、输入及用户动作 | 可判定的结果及数据读回 | 测试、API 或浏览器操作记录 |

## 未决问题与接续关系

待决问题、影响与处理方式；如替代旧规范，列明被替代范围并链接。
无未决问题则明确注明。
```

优先沿用已有 E/PV/DS 等编号；新增编号在本文内唯一，引用时同时标注 spec 路径。验收不能只写“功能正常”或“测试通过”；按实际风险覆盖适用的失败、权限、空状态与恢复结果。fixture 和真实源证据分开，不能互相冒充。

## 4. Plan 与切片模板

```markdown
# <能力名称>实施计划

日期：YYYY-MM-DD
依据：对应 spec、开发指南及已有路线图链接
执行范围：已授权哪些切片与操作，哪些仍待决；按实际授权填写

## 切片总览

| 切片 | 可交付结果 | 依赖 | 验收编号 | 当前进展及证据 |
| --- | --- | --- | --- | --- |
| S1 | 一个完整的可操作结果 | 无 / 已有能力 | spec 路径 + AC01 | 待开始 |
| S2 | 在 S1 上增加的完整结果 | S1 的明确交付 | spec 路径 + AC02 | 待开始 |

## S1：<交付名称>

- 目标与用户动作：用户能完成什么；基础设施切片说明技术结果。
- 范围与非目标：本片改变什么、明确不改变什么。
- 依赖与前置条件：需要的契约、基线或环境，以及如何判断已满足。
- 关键约束：引用 spec；必要时注明实际风险及理由，分级遵循开发指南。
- 实施建议：可能涉及的模块与复用点，实施者可调整非契约细节。
- 验收：对应编号、可执行步骤、预期结果及需保留的证据。
- 完成条件：相关检查及本片 agent 验收通过，证据对应实际代码身份。
- 交接与升级：可自主决定的细节、本片待决问题及需升级的边界。

## 后续切片

近期按 S1 结构展开；远期只列目标、依赖和验收编号。

## 整体收口

明确跨切片旅程与整体验收的责任切片，不以所有局部测试通过替代整体结果。
验收、合并、部署分别记录；检查和发布门槛引用开发指南，不复制另一套规则。
```

切片原则：

- 按用户可体验的纵向流程拆，例如“创建 → 列表可见 → 详情读回”，不默认拆成“全部后端 → 全部前端 → 统一测试”。基础设施准备可以独立成片，但须有可验证的技术退出条件。
- 独立验收不等于没有依赖；依赖应写清前一片必须交付的能力，不能只写“等上一片完成”。
- 每片由一个实施负责人完成实现、相关测试、预览与产品验收，不默认另设编码、测试和验收 agent。
- 默认串行；确有独立边界且获得并行开发授权时才安排多个 agent，明确文件、worktree 和预览环境归属。
- 进度集中在总览中更新并引用证据；切片正文维护执行要求，不再抄一遍状态。区分待开始、实施中、阻塞、已实现待验收、agent 验收通过；合并和部署记录实际事实，不由验收状态推断。

## 5. 交接、自主决策与完成回报

实施 agent 开始时核对实际代码和前置条件，不重新规划已批准的整个需求。契约不变的内部实现、测试组织和局部修复自主决定；如出现需求冲突、扩大范围、改变关键契约或缺少必要授权，说明具体影响后升级讨论，不能静默改 spec 降低要求。

预览可用即提供地址、访问方式、代码身份、数据模式与限制；产品验收由实施 agent 自己完成，通过后继续已授权流程，不等待用户反馈或再询问是否继续。只授权 S1 时不能把整份 plan 当作实施所有切片的授权。

完成回报只需：交付结果、代码身份、适用的预览地址、验收编号与证据、剩余问题，以及已更新的 plan。普通切片不默认再交回规划 agent 做一轮重复评审；风险分级、独立评审和合并要求统一引用[开发指南 §3](development-guide.md#3-验证与-review-按风险缩放)。

以下交接指令可直接复用，替换实际路径和切片范围：

```text
规划：按 docs/planning-guide.md 规划这个需求，形成或更新 spec 和 plan，供其它 agent 实施。

实施：依据 <spec 路径> 和 <plan 路径> 实施 S1，完成相关测试和 agent 验收，
预览可用即提供地址，更新 plan 中的状态与证据。按已授权范围继续，不等待用户验收确认。
```

## 6. 规划交付前自查

- 目标、非目标与关键约束明确，假设和未决问题没有伪装成批准事实。
- 所有必需验收项映射到切片，整体旅程有收口位置，依赖无循环。
- 近期切片可直接实施，远期没有不必要的逐文件施工设计。
- spec 与 plan 互链，已有规范未重复创建，当前进度只有一个维护位置。
- 没有新增逐片审批、普通切片强制独立 review、自动子代理或生产授权。
- 运行 `bash scripts/ci.sh docs`，并人工核对语义与规则冲突；仅规划文档变化不机械运行无关全量测试。
